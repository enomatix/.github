# Contributing to Enomatix

Thank you for your interest in contributing to an Enomatix project.

Our goal is to build reliable, secure and maintainable software. Every contribution, whether it is code, documentation, testing or design, should help improve the quality of our products.

## Before you begin

Before contributing, please:

- Read the project documentation
- Check for existing issues and pull requests
- Open an issue for significant changes before beginning implementation
- Keep discussions respectful and constructive

## Development environment

Contributors should use a modern development environment with:

- Git
- Node.js (where applicable)
- Visual Studio Code or another suitable editor
- A supported operating system

Project-specific requirements are documented within each repository.

## Branching

Unless otherwise documented:

- Create a feature branch from `main`
- Keep branches focused on a single change
- Rebase regularly to minimise merge conflicts

Example branch names:

- `feature/add-user-authentication`
- `fix/login-validation`
- `docs/update-api-guide`

## Commit messages

Write clear, descriptive commit messages.

Good examples:

```text
Add password reset endpoint

Fix validation for customer addresses

Update deployment documentation
```

Avoid messages such as:

```text
Update

Changes

Fix stuff
```

Every commit should represent a logical unit of work.

## Code quality

All contributions should:

- Be readable and maintainable
- Follow the project's coding standards
- Avoid unnecessary complexity
- Include appropriate comments where they improve understanding
- Remove dead code rather than leaving it commented out

## Testing

Where applicable:

- Run existing tests before submitting changes
- Add tests for new functionality
- Ensure bug fixes include regression tests when practical

Changes that introduce failing tests should not be submitted.

## Documentation

Documentation is part of the product.

Please update documentation whenever changes affect:

- Installation
- Configuration
- APIs
- User workflows
- Developer workflows

## Security

Security should be considered throughout development.

If you discover a security vulnerability, please follow the instructions in the organisation's `SECURITY.md` file rather than opening a public issue.

## Pull requests

Before opening a pull request, ensure that:

- The change is complete
- Tests pass
- Documentation has been updated where necessary
- Commit history is clean
- The pull request description clearly explains the purpose of the change

Reviews should focus on improving quality through constructive feedback.

## Code of conduct

Treat all contributors with professionalism and respect.

We value thoughtful discussion, collaboration and continuous learning.

## Questions

If you are unsure about any aspect of contributing, please open a discussion or issue before starting significant work.
